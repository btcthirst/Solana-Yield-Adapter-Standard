# Drift: SDK-спроба та перевірка дискримінаторів — висновки

> Сесія 2026-06-07, гілка `feat/drift` (на рівні `develop`, без власних комітів).
> Мета: (1) перевірити, чи варто перейти на офіційний `drift` SDK замість ручного CPI;
> (2) перевірити теорію «v3-апгрейд змінив дискримінатори» з `drift-fork-issues.md`.

---

## 1. SDK Drift (`drift::cpi::*`) — НЕ ВАРІАНТ

Підхід `use drift::cpi::deposit_insurance_fund_stake` тощо протестовано реально (`cargo add` + резолв).

**Причина А — залежності не резолвляться (до компіляції не доходить):**

```
drift v2.162.0 → pyth_lazer → serde_json =1.0.143 (точна версія)
   ✗ конфлікт з
наш anchor-lang v1.0.2 → anchor-lang-idl 0.1.2 → serde_json 1.0.150
```

`drift` зібраний під старий стек (Anchor 0.29–0.30, Solana 1.16–1.18, тягне `serum-dex`,
`pyth`, `pyth_lazer`), а воркспейс — Anchor 1.0 / Solana 3.1. Несумісні покоління.
Resolver падає на `serde_json`.

**Причина Б — навіть якби зібралось, нічого не дає:**
`drift` не публікується на crates.io (там `drift v0.2.0` — сторонній крейт). Тягнеться як
git-залежність із `protocol-v2`, де HEAD = `v2.162.0` (rev `0ae3e3b1`) = **pre-upgrade**.
Той самий макрос Anchor згенерував би **байт-у-байт ті самі** дискримінатори, що вже є в
нашому `cpi.rs` (`add_insurance_fund_stake → fb90730b…`).

**Висновок:** ручний CPI у `cpi.rs` лишаємо. Він компілюється під сучасний стек і його
легко перенаправити на правильні диски, щойно вони з'являться. Гілку лишено чистою
(`Cargo.toml` відновлено, без комітів).

## 2. Дискримінатори = офіційний on-chain IDL (теорія «v3 змінив диски» ПІД СУМНІВОМ)

Користувач витяг on-chain IDL з експлорера (`idl.json`): **version `2.150.0`**, старий
Anchor-формат (ключі `name/accounts/args`, без явних `discriminator` → диски деривуються
через `sha256("global:<snake_name>")`). Імена в IDL — camelCase (`addInsuranceFundStake`),
тож для деривації конвертуються назад у snake_case.

Порахували всі 5 IF-інструкцій і звірили з константами `cpi.rs`:

| Інструкція | IDL-derived | наш `DISC_*` | |
|---|---|---|---|
| `initialize_user_stats` | `fef34862fb82a8d5` | `fef34862fb82a8d5` | ✓ |
| `initialize_insurance_fund_stake` | `bbb3f346f85a5c93` | `bbb3f346f85a5c93` | ✓ |
| `add_insurance_fund_stake` | `fb90730bde2f3eec` | `fb90730bde2f3eec` | ✓ |
| `request_remove_insurance_fund_stake` | `8e46cc5c496ab434` | `8e46cc5c496ab434` | ✓ |
| `remove_insurance_fund_stake` | `80a68e09febb8fae` | `80a68e09febb8fae` | ✓ |

**Усі 5 збігаються байт-у-байт.**

Це **спершу** породило сумнів у старому root-cause: якщо наші диски = офіційний on-chain
IDL, який публікує сам авторитет програми, то «Drift змінив диски» вимагало б, щоб
задеплоєна програма розійшлася з власним IDL. Цей сумнів **перевірено наживо й знято** ↓

### ВИРІШАЛЬНИЙ ТЕСТ: live `simulateTransaction` проти mainnet (Helius)

Зібрано вручну легасі-tx, що викликає `dRifty` з `data = <disc> + u64`, і засимульовано з
`sigVerify=false`, `replaceRecentBlockhash=true`:

| Дискримінатор | Результат | CU | Лог |
|---|---|---|---|
| `fb90730bde2f3eec` (add_insurance_fund_stake) | `InstructionError Custom(101)` | 1829 | `AnchorError … InstructionFallbackNotFound` |
| `ffffffffffffffff` (свідомо сміттєвий, контроль) | `InstructionError Custom(101)` | 1829 | `AnchorError … InstructionFallbackNotFound` |

**Жива програма поводиться з `fb90730b` ТОЧНО як зі сміттям** — однакова помилка, однакові CU.
Anchor-диспетчер виконався і не знайшов інструкцію під цей диск.

**Висновок: on-chain IDL v2.150 ЗАСТАРІВ і НЕ відповідає задеплоєній програмі. Диски справді
змінилися при апгрідіі. Старий root-cause у `drift-fork-issues.md` — ПРАВИЛЬНИЙ.**

### Додаткові докази (Helius)

- **IF-vault `2CqkQvYx…` замовк на апгрідіі:** найсвіжіші tx — `2026-04-02` (слот ~410.4M, тобто
  *перед* апгрейдом `410633860`); після апгрейду — **жодної**.
- **Програма `dRifty` фактично ДРІМАЄ:** у 20 свіжих повних блоках (~26k tx) і 15 найновіших
  сигнатурах — **0 реальних викликів**; усі згадки `dRifty` — read-only через address-lookup-tables
  (інші протоколи читають Drift-акаунти як оракул/маркет-дані). `getSignaturesForAddress` тут
  марний для пошуку дисків.
- Поточний слот mainnet: `424,827,210` (апгрейд ~14M слотів тому).

Тобто активність Drift і/або модель IF-стейкінгу, схоже, **переїхали** з цього набору інструкцій
(узгоджується з теорією v3 «DSM»).

## 3. Як розблокувати

Блокер **підтверджено зовнішнім** — потрібні **реальні дискримінатори/IDL v3**, яких нема в
жодному публічному джерелі. Шляхи:

1. Дістати v3 IDL напряму від Drift (Discord `#research-and-dev-chat`) або через bounty-команду.
2. З'ясувати, **куди переїхав** IF-стейкінг / трейдинг (новий program ID або нові інструкції),
   і відновити диски з реального post-upgrade виклику там. На `dRifty` його зараз не видно.
3. Окремо: чи v3/DSM узагалі підтримує USDC-IF-стейкінг у формі, яку реалізує адаптер
   (можливо, модель змінилась на стейк DRIFT-токена в per-asset пули).

> Спроби дістати диски програмно з `dRifty` (block-scan, getSignaturesForAddress) **марні** —
> програма дрімає. Без офіційного v3 IDL не обійтися.
