# Аналіз завдання: Solana Yield Adapter Standard

## Чи можливо виконати?

**Так, але це складний проект** рівня Senior Solana developer. Не неможливий, але потребує глибоких знань екосистеми Solana та DeFi-протоколів.

---

## Розбивка по компонентах

### 1. Core Dispatcher Contract — складність: середня

Anchor-програма-роутер зі стандартним інтерфейсом `deposit / withdraw / current_value`.

Головний виклик — правильне проектування CPI (Cross-Program Invocation) boundary та обробка різних account layouts різних протоколів через єдиний уніфікований інтерфейс.

### 2. П'ять адаптерів — складність: висока (різна для кожного)

| Адаптер | Складність | Причина |
|---|---|---|
| **MarginFi USDC** | ★★★☆☆ | Добре задокументований, є офіційний SDK |
| **Drift Insurance Fund** | ★★★☆☆ | Зрозумілий стейкінг-механізм, є SDK |
| **Kamino USDC** | ★★★★☆ | Складна vault-архітектура, share accounting |
| **Jupiter LP** | ★★★★☆ | Складна AMM-механіка, перп-позиції |
| **Maple Finance** | ★★★★★ | Permissioned pools, інституційна логіка, менша документація |

### 3. On-Chain Registry з governance-gate — складність: середня

Механізм авторизації для реєстрації нових адаптерів. Потребує уважного проектування:
- хто може approve нові адаптери
- як зберігаються метадані адаптерів on-chain
- механізм revoke/pause для скомпрометованих адаптерів

### 4. Mainnet-Fork Tests — складність: висока

Це **найбільш ризикова** частина проекту. Потрібно:
- клонувати реальні mainnet-акаунти (vaults, price feeds, user positions)
- запускати тести проти них локально

Інструмент — **Surfpool**, який дозволяє локально форкнути mainnet state з реальними акаунтами.

### 5. Документація — складність: низька

Markdown-специфікація та "Build your own adapter" гайд — це час, а не технічна складність.

## Що необхідно для виконання

### Технічні навички

- Глибокий Rust + Anchor (не початківець рівень)
- Розуміння Solana account model, PDAs, CPIs
- Знання DeFi-механік (yield, LP shares, AMM, insurance funds)
- TypeScript для тестів та клієнтського коду

### Інструменти та залежності

| Ресурс | Призначення |
|---|---|
| Mainnet RPC (Helius / QuickNode) | Клонування акаунтів для тестів |
| Surfpool | Mainnet-fork локальне тестування |
| IDL-файли всіх 5 протоколів | CPI-виклики |
| `@kamino-finance/klend-sdk` | Kamino адаптер |
| `@mrgnlabs/marginfi-client-v2` | MarginFi адаптер |
| `@jup-ag/api` | Jupiter LP адаптер |
| `@driftprotocol/sdk` | Drift адаптер |
| Pyth / Switchboard | Oracle pricing для `current_value` |

### Потенційні блокери

- **Maple Finance** — найменш задокументований протокол, можуть бути закриті або нестабільні RPC endpoints
- **Jupiter LP** — перп-система складна, IDL може бути неповним або частково закритим
- **`current_value`** для LP-позицій потребує oracle pricing (Pyth/Switchboard), що додає складності
- **Mainnet-fork стабільність** — тести залежать від зовнішнього стану, можуть бути флакі

## Рекомендована послідовність розробки

1. **Спочатку** — спроектувати core dispatcher interface та adapter trait (Rust trait або Anchor account constraint pattern)
2. **MarginFi** — найпростіший адаптер, відпрацювати архітектуру
3. **Drift** — підтвердити що патерн масштабується
4. **Registry** — реалізувати після того як є 2 робочих адаптери
5. **Kamino** — застосувати відпрацьований патерн до складнішого протоколу
6. **Jupiter LP** — найскладніша AMM-логіка
7. **Maple** — окремий challenge через permissioned nature
8. **Mainnet-fork тести** — паралельно з адаптерами, але фінальна верифікація в кінці
9. **Документація** — після стабілізації інтерфейсу

## Висновок

Проект **реалістичний** для виконання, але вимагає:
- Мінімум одного Senior Solana Rust developer
- Доступу до якісного mainnet RPC
- Глибокого занурення в архітектуру кожного з 5 протоколів

Найбільша технічна невизначеність — **Maple Finance** та стабільність mainnet-fork тестів. Рекомендовано починати з MarginFi та Drift для відпрацювання загальної архітектури, а потім масштабувати на складніші протоколи.
